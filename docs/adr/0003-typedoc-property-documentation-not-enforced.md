# 0003 — TypeDoc no longer enforces documentation on properties

- **Status:** Accepted
- **Date:** 2026-08-07
- **Supersedes:** nothing (narrows a rule introduced with the Phase 3 docs system)
- **Deciders:** Bernardo (product), CTO (architecture)

## Context

Master Plan §5.1 says "code without a doc-comment is unfinished code," and Phase 3
made that enforceable rather than aspirational: `typedoc.base.json` sets
`validation.notDocumented` with `treatWarningsAsErrors`, so `pnpm run docs` fails when
an exported symbol carries no TSDoc comment. TypeDoc's default
`requiredToBeDocumented` list includes `Property`.

Introducing the M2 state model made that setting unworkable. GDD §15 requires roles,
stats, ranges and pitch dimensions to be **Zod-validated data**, so the state model is
built from Zod schemas — including `z.enum([...])` for `Team` and `Role`.

A `z.enum()` schema exposes one internal property per member. TypeDoc reports each as
an undocumented `Property`:

```
@gaffer/shared.RoleSchema.__type.striker (Property) does not have any documentation
@gaffer/shared.TeamSchema.__type.home (Property)    does not have any documentation
```

Thirty such warnings appeared from two enums, and they multiply: every schema that
embeds `RoleSchema` or `TeamSchema` re-reports the same members through its own
inferred type. There is **no source location to attach a comment to** — these
properties are generated by Zod's types, not written by us. No TSDoc comment, `@hidden`
tag, or exclusion pattern can reach them.

That left three options:

1. Stop using `z.enum`, hand-rolling union schemas instead.
2. Disable `validation.notDocumented` entirely.
3. Narrow `requiredToBeDocumented` to exclude `Property`.

## Decision

Option 3. `typedoc.base.json` now sets `requiredToBeDocumented` to TypeDoc's default
list **minus `Property`**:

```json
["Enum", "Variable", "Function", "Class", "Interface", "Method", "Accessor", "TypeAlias"]
```

Everything a developer names and exports is still enforced. Object-shape properties
are still documented by hand throughout the codebase — that is now convention rather
than a gate.

## Rationale

- **Option 1 was the worst trade.** `z.enum` is the idiomatic way to express a closed
  set in Zod, gives a clean `z.infer` union, and is what GDD §15's data-driven design
  leans on. Distorting the domain model to satisfy a docs linter is the tail wagging
  the dog.
- **Option 2 threw away too much.** Most of the value of `notDocumented` is catching an
  exported _function_ or _type_ that nobody explained. That risk is real and this
  keeps guarding it.
- **Option 3 loses the least.** The properties we actually author are few, visible in
  review, and already documented. The properties we cannot author are exactly the ones
  now excluded.

## Consequences

**Positive**

- `pnpm run docs` passes on a Zod-based codebase without weakening the checks that
  matter. Verified after the change: an exported function with no comment still exits
  non-zero.
- The domain model stays idiomatic Zod.

**Negative / accepted costs**

- A new property on an object schema can now ship undocumented without CI complaining.
  Mitigated by convention and code review, not by tooling. If this starts slipping,
  the answer is a custom lint rule over our own source, not re-enabling a TypeDoc
  check that cannot distinguish our properties from Zod's.
- The enforcement story is now "most kinds" rather than "everything," which is a
  slightly weaker claim than Phase 3 made. This ADR exists so that weakening is
  recorded rather than discovered later in a config diff.

**Revisit if**

- TypeDoc gains a way to scope `notDocumented` to first-party source locations, or to
  exclude symbols originating in `node_modules` types.
- We stop using Zod, or Zod stops exposing enum members as properties.
- Undocumented properties become a real problem in review, at which point a bespoke
  ESLint rule over `packages/*/src` is the better instrument.
